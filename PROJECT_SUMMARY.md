# Campaign API: Project Summary and Test Evidence

**Oct 1, 2026**

## Summary

I built a secured public REST API for managing email campaigns, and every feature below was exercised end-to-end against a running instance on 1 October 2026 — all checks passed.

This is a focused slice of what a production campaign/mailing-list API needs: full CRUD with soft delete, input validation with clear per-field errors, API-key authentication with read/write scopes, per-key rate limiting, and self-service OpenAPI documentation. It deliberately does **not** try to be feature-complete — pagination, a shared multi-instance rate-limit store, and an API gateway are scoped out and listed under "Next steps" rather than built, so the project stays reviewable in one sitting.

Parts of this were built with Claude Code (an AI coding agent) working from my direction, with every change compiled, tested against a real Postgres instance, and reviewed before being accepted — see "How the AI coding agent was used" below.

## What the API does

The API lets another program manage **campaigns** (think: an email blast or mailing list) over HTTP — create one, look it up, rename it, delete it — without a person clicking through a UI. Every request passes through the same five checks before it's allowed to touch stored data:

1. **Who are you?** — Is the API key real and not revoked? → `401` if not.
2. **Asking too often?** — Burst of 5, then 1 every 2 seconds, per key → `429` if exceeded.
3. **Allowed to do this?** — Read-only keys can't write → `403` if not.
4. **Does the request make sense?** — Required fields present, body is valid JSON → `400` if not.
5. **Business rules** — Does the campaign exist? Is the name already taken? → `404` / `409` if not.

Only after all five pass does the request reach the database.

| Term | What it means |
|---|---|
| API key | A secret string identifying a client; stored only as a SHA-256 hash, never in plaintext |
| Scope | What a key may do — `campaigns:read` or `campaigns:write` |
| Soft delete | Hiding a record instead of erasing it, so it's excluded from reads but recoverable |
| Rate limit | A cap on requests per key in a time window, enforced with a token bucket |

## Features and test evidence

All evidence below is real `curl -i` output against the running API on `localhost:8081`, captured on 1 October 2026.

### 1. The system creates its own storage on startup

No manual database setup — Hibernate creates both tables from the JPA entities on first boot:

```
Hibernate:
    create table api_keys (
        id bigint generated by default as identity,
        created_at timestamp(6) with time zone,
        key_hash varchar(255),
        ...
Hibernate:
    create table campaigns (
        id varchar(255) not null,
        deleted boolean not null,
        name varchar(255),
        ...
```

### 2. Self-service documentation (OpenAPI/Swagger)

`/v3/api-docs` and `/swagger-ui/index.html` are public — reachable with no API key — and generated from the controller code, so they can't drift out of date. Every endpoint lists exactly the status codes it can actually return:

```
GET    /api/v1/campaigns      -> 200, 401, 403, 429
POST   /api/v1/campaigns      -> 201, 400, 401, 403, 429
GET    /api/v1/campaigns/{id} -> 200, 401, 403, 404, 429
PATCH  /api/v1/campaigns/{id} -> 400, 401, 403, 404, 409, 429
DELETE /api/v1/campaigns/{id} -> 204, 401, 403, 404, 429
```

### 3. Access control with API keys

Keys are hashed (SHA-256) before storage — a leaked database reveals nothing. Missing and invalid keys get the identical 401 message, so an attacker can't tell which keys exist.

| Test | Expected | Result |
|---|---|---|
| No key | 401 | **Pass** |
| Fake key | 401 | **Pass** |
| Read-only key views campaigns | 200 | **Pass** |
| Read-only key tries to create | 403 | **Pass** |
| Full-access key creates | 201 | **Pass** |

```
$ curl -i http://localhost:8081/api/v1/campaigns
HTTP/1.1 401
{"message":"Missing or invalid API key. Send it in the X-API-Key header.","status":401}

$ curl -i http://localhost:8081/api/v1/campaigns -H "X-API-Key: fake_abc123"
HTTP/1.1 401
{"message":"Missing or invalid API key. Send it in the X-API-Key header.","status":401}

$ curl -i http://localhost:8081/api/v1/campaigns -H "X-API-Key: $READ_KEY"
HTTP/1.1 200
X-RateLimit-Limit: 5
X-RateLimit-Remaining: 4
[]

$ curl -i -X POST http://localhost:8081/api/v1/campaigns -H "X-API-Key: $READ_KEY" \
    -d '{"name":"Should Fail","subject":"x"}'
HTTP/1.1 403
{"message":"This API key does not have permission for this action.","status":403}
```

### 4. Creating and listing campaigns

```
$ curl -i -X POST .../campaigns -H "X-API-Key: $WRITE_KEY" \
    -d '{"name":"Weekly Newsletter","subject":"news@shop.com weekly digest"}'
HTTP/1.1 201
Location: /api/v1/campaigns/cmp_8be1e159-f786-4409-b269-4e251cbfc5fe
{"id":"cmp_8be1e159-...","name":"Weekly Newsletter","subject":"news@shop.com weekly digest","status":"DRAFT"}

$ curl -i .../campaigns -H "X-API-Key: $READ_KEY"
HTTP/1.1 200
[{"id":"cmp_8be1e159-...","name":"Weekly Newsletter",...},{"id":"cmp_6d84fc32-...","name":"VIP Customers",...}]
```

IDs are random (`cmp_<uuid>`), never sequential/guessable. Responses expose only the four public fields — `id`, `name`, `subject`, `status` — never internal columns like `deleted`.

### 5. Updating a campaign

A campaign can be renamed. Two campaigns can't share a name, but renaming to your **own** name in different capitalization is allowed — the tricky case.

| Test | Expected | Result |
|---|---|---|
| Rename to "Monthly Newsletter" | 200 | **Pass** |
| Rename to "MONTHLY NEWSLETTER" (own name, different case) | 200 | **Pass** |
| Rename to "vip customers" (another campaign's name) | 409 | **Pass** |

```
$ curl -i -X PATCH .../campaigns/$ID -H "X-API-Key: $WRITE_KEY" -d '{"name":"vip customers"}'
HTTP/1.1 409
{"message":"A campaign named 'vip customers' already exists","status":409}
```

### 6. Input checking and clear error messages

| Test | Expected | Result |
|---|---|---|
| Empty name and subject | 400, one message per field | **Pass** |
| Malformed JSON body | 400, clean format | **Pass** |
| Campaign that doesn't exist | 404 | **Pass** |

```
$ curl -i -X POST .../campaigns -H "X-API-Key: $WRITE_KEY" -d '{"name":"","subject":""}'
HTTP/1.1 400
{"status":400,"message":"Validation failed","errors":{"subject":"Campaign subject is required","name":"Campaign name is required"}}

$ curl -i -X POST .../campaigns -H "X-API-Key: $WRITE_KEY" -d '{oops'
HTTP/1.1 400
{"message":"Request body is missing or is not valid JSON","status":400}
```

The malformed-JSON case above was caught *during this test pass* — the first version leaked a full Java stack trace via Spring's default error page instead of our error format. Fixed by adding an `HttpMessageNotReadableException` handler to `GlobalExceptionHandler`; retested and confirmed clean.

### 7. Safe deletion

```
$ curl -i -X DELETE .../campaigns/$ID -H "X-API-Key: $WRITE_KEY"
HTTP/1.1 204

$ curl -i .../campaigns/$ID -H "X-API-Key: $READ_KEY"
HTTP/1.1 404
{"message":"Campaign not found: cmp_8be1e159-...","status":404}
```

Deletion hides the record (204, then 404 on lookup) but keeps the row in Postgres — recoverable, and kept for audit.

### 8. Protection against overload

Each key gets a burst of 5 requests, then 1 every 2 seconds. 8 rapid requests from a freshly-refilled key gave exactly 5 successes and 3 rejections:

```
Request 1 -> 200
Request 2 -> 200
Request 3 -> 200
Request 4 -> 200
Request 5 -> 200
Request 6 -> 429
Request 7 -> 429
Request 8 -> 429

$ curl -i .../campaigns -H "X-API-Key: $READ_KEY"
HTTP/1.1 429
X-RateLimit-Limit: 5
X-RateLimit-Remaining: 0
Retry-After: 2
{"message":"Too many requests. Retry after 2 second(s).","status":429}
```

Every response — success or not — carries `X-RateLimit-Limit` / `X-RateLimit-Remaining`, and different keys have independent buckets (confirmed separately).

## How the AI coding agent was used

Claude Code implemented several pieces of this project (PATCH/soft-DELETE, API key auth, rate limiting, OpenAPI docs, the test suite) from my direction, following this loop for each feature:

1. **Agreed scope first.** Before any code, we explicitly narrowed a larger roadmap (15 possible features) down to 8 worth building for a showcase, and dropped an API Gateway as "documented, not built" — a deliberate scope decision, not a shortcut.
2. **Verified against the real stack, not just compiled.** Every feature was exercised with real `curl` requests against a running instance backed by actual Postgres — not just `mvn compile` — including edge cases called out explicitly (self-rename case-change, duplicate name, burst rate limiting).
3. **Treated test failures as signal.** Writing the unit test suite surfaced a genuine off-by-one in the rate limiter's "remaining count" test (fixed), and a pre-existing broken test (`CampaignApiApplicationTests` lived in the wrong Java package, so Spring Boot couldn't find its configuration — this would have failed the first time anyone ran `mvn test`, unrelated to any of this session's feature work).
4. **Found and fixed a real bug while gathering evidence for this document.** Malformed JSON was leaking a full stack trace via Spring's default error handler instead of the API's own error format (see section 6 above) — caught because evidence was captured against the running server rather than assumed from the code.

## Known limitations and next steps

| Limitation | Why it matters | Recommended fix |
|---|---|---|
| No version control | Changes aren't tracked or revertible | Initialize git, commit a baseline before further changes |
| Duplicate-name check and save aren't atomic | Two simultaneous renames to the same name could both pass | Add a unique index on `lower(name)` for non-deleted rows |
| Rate limiter is in-memory, single-instance | A multi-instance deployment lets a client exceed its real limit | Shared counter (Redis) or enforce at a gateway |
| No pagination | Slow for accounts with many campaigns | Page results, e.g. 50 at a time |
| No Flyway/Liquibase | Schema changes rely on `ddl-auto=update`, risky for prod | Managed migrations |
| Dev API keys printed at startup | Fine for local testing only | Issue keys through a secured admin flow |
| No CI | A future change could break something unnoticed | Automated tests + CI on push |
| API Gateway | Centralized routing/auth/rate-limiting across services | Deliberately out of scope for a single-service project — documented here rather than built |
